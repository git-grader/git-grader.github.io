Push code. Capture proof.
Grade safely.

GitGrader is an open-source, self-hostable platform for courses that accept programming assignments over Git. Students register an SSH key, push signed work, and get an unguessable result link; instructors run the whole course from one workspace; every grading run happens in a throwaway, networkless container.

Demo on localhost:8080 · sign in as instructor / password · sample course included

How it works

A trusted path from push to proof

Every accepted push becomes a durable submission and a reproducible grading event. Nothing runs on the host, and every result points back to the exact template, test suite, runtime, and commit that produced it.

01

Register

Students enrol an SSH public key at /register. There is no student account to create or password to reset.

02

Push

Work arrives over SSH. Commits must be signed with a registered key; unsigned commits, oversized pushes, and rewritten history are refused.

03

Capture

The push becomes an immutable, append-only submission. Only the newest queued attempt is graded; older ones are cancelled, never lost.

04

Run

The application asks a separate runner for a sandbox. The sandbox has no network, no capabilities, and a read-only root.

05

Grade

Hidden tests run against the suite manifest. Each declared test reports an outcome, and per-test weights decide the score.

06

Review

The push prints a result link and a standing overview. Instructors see submissions, class progress, and exports.

Principles

Built for courses that need control

Git-native

Submission is a git push. No upload portals, no zip files, no plugins, no new client to teach.

No student accounts

A registered SSH key identifies a student when pushing. An unguessable link is the only credential needed to read a result.

Auditable

Submissions, grading runs, and audit events are append-only. Regrades add evidence; they do not rewrite it.

Isolated by construction

The web application builds no Docker client at all. A separate runner holds the socket and only ever starts a sandbox.

Fair under load

One job per student, newest-wins coalescing, queue ceilings, and rolling hourly push allowances keep one student from crowding the course.

Self-hostable

Your institution keeps operational and data control. PostgreSQL, Docker, and LDAP — no external services required.

One workspace

Two paths, one course record

Students get the shortest possible path to feedback. Instructors and administrators get the controls a real cohort needs — and the server, not the browser, is the authority for every one of them.

For students

Register once, push, read

  • Self-register an SSH key for the course and class — up to five keys by default
  • Clone a starter repository per assignment, with the non-default SSH port already handled
  • Push signed commits and see the score, allowed hints, and result link in the terminal
  • Keep a standing overview of every course and assignment result in one page
  • No account, no password — each accepted push returns a result link, and the standing overview link is rotated on every push
For instructors & administrators

Run the whole course

  • Courses, classes, and registration windows with student verification, suspension, and key management
  • Materials with versioned public templates and confidential hidden test suites
  • Assignments with runtime, schedule, grading limits, and individual deadline extensions
  • Submissions, class progress, and reports exported as CSV, JSON, or XLSX
  • Administration for audit log, settings, and runtimes, with LDAP-backed sign-in
Features

Evidence, not promises

  • Git-over-SSH admission with registered-key and SSHSIG signature checks; signed commits required by default
  • Push admission limits on total size, file size, file count, and new commits; non-fast-forward and duplicate commits refused
  • Versioned starter templates and hidden test suites students cannot read
  • Manifest-declared tests with per-test weights, categories, and didactic hints; a suite without a manifest is refused
  • Runtimes pinned by image digest, with single- and two-container topologies; a shimmed run keeps hidden tests in a container the submission cannot mount
  • Hardened sandboxes: no network, read-only root, dropped capabilities, no-new-privileges, CPU/memory/PID caps, and a timeout
  • Append-only submissions and grading runs; regrades add a run instead of overwriting the previous result
  • Fair dispatch: newest-wins coalescing, one job per student, queue ceilings, and rolling hourly push allowances
  • Opaque result tokens stored only as hashes, plus a standing results overview rotated on every accepted push
  • LDAP instructor/admin authentication, audit events with HMAC-hashed client addresses, and per-address rate limits
  • Fixed-query course reports and CSV, JSON, and XLSX exports for snapshots outside GitGrader
  • OpenAPI contract at /api/v1/openapi and Swagger UI at /api/v1/docs — disabled under production by default

Honest about limitations: GitGrader is a grading and submission system, not an authorship detector. A verified signature proves a commit was signed by a key registered to that student, not that the student wrote the work unaided. It also runs untrusted code, so read the security model before exposing an instance to anyone else.
Quick start

Deploy your own grader

# needs Docker and, for the first build, JDK 25
git clone https://github.com/git-grader/gitgrader
cd gitgrader
./scripts/install.sh --demo  # build, start, and load the sample course
scripts/verify-install.sh    # readiness, API meta, SSH reachability

The demo comes up on http://localhost:8080 with a sample course, a starter project, and hidden tests. Sign in as instructor / password, or register a student key at /register. The reference solution deliberately scores 7 of 10 (70.0 %) — a different number means something is wrong.

Leave off --demo for an empty instance. Before anyone else uses it, set both database passwords, a real APP_PUBLIC_URL (HTTPS), the public SSH host and port, and a random GRADING_RUNNER_API_SECRET. Full details in the installation guide and the manual testing walkthrough.
